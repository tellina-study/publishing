# Sources — curated reading list

Durable, reusable sources worth citing again. Track the **manifest here**, not the binaries
(PDFs/epubs live in `sources/files/` and are gitignored). Add a row when the `researcher` finds
a source worth keeping.

| Source | Type | Topic(s) | Link / ID | Reliability | Notes |
|--------|------|----------|-----------|-------------|-------|
| <a id="lost-in-the-middle"></a>Lost in the Middle (Liu et al., 2023) | primary | context-engineering, placement | [arXiv:2307.03172](https://arxiv.org/abs/2307.03172) | high | U-shaped position effect: models attend to the edges of the context, the middle sags. |
| <a id="tokenizer-tax"></a>Tokenizer Tax across 25 European languages (2026) | primary | tokenization | [arXiv:2605.24718](https://arxiv.org/abs/2605.24718) | high | First controlled comparison on parallel texts; Slavic languages most expensive, English cheapest. |
| <a id="petrov-tokenizer"></a>Petrov et al., Language Model Tokenizers (2023) | primary | tokenization | [arXiv:2305.15425](https://arxiv.org/abs/2305.15425) | high | >4× token gap for some language pairs; English carries the smallest markup. |
| <a id="toon-benchmark"></a>TOON format + benchmark | secondary | prompt-packaging, formats | [github.com/toon-format/toon](https://github.com/toon-format/toon) | medium | Token-oriented format vs JSON; data-shape/baseline tradeoff, not always a win. |
| <a id="toon-matveev"></a>Matveev, independent TOON measurement (2026) | primary | prompt-packaging, formats | [arXiv:2603.03306](https://arxiv.org/abs/2603.03306) | high | Independent check on TOON token/accuracy claims. |
| <a id="caveman-hakim"></a>Hakim, Brevity Constraints (2026) | primary | prompt-packaging, brevity | [arXiv:2604.00025](https://arxiv.org/abs/2604.00025) | high | Brevity / caveman-prompt savings are modest (~15–20%), not −75%. |
| <a id="language-confusion"></a>Language Confusion (EMNLP 2024) | primary | language, placement | [arXiv:2406.20052](https://arxiv.org/abs/2406.20052) | high | Isolated language instruction confuses less than an integrated one; one example ≈80% correct-language. |
| <a id="chinese-mythbuster"></a>Mythbuster: Chinese is not more efficient (2026) | primary | tokenization, language | [arXiv:2604.14210](https://arxiv.org/abs/2604.14210) | medium | Preprint; the Chinese-saves-tokens claim is unconfirmed and model-dependent. |
| <a id="anthropic-context-engineering"></a>Anthropic — effective context engineering | secondary | context-engineering | [anthropic.com](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | high | Effective context < spec window; what fills the budget matters. |
| <a id="bahdanau-attention"></a>Bahdanau, Cho, Bengio — Neural MT by Jointly Learning to Align and Translate (2014) | primary | transformers, attention, machine-translation | [arXiv:1409.0473](https://arxiv.org/abs/1409.0473) | high | Origin of the attention mechanism; a bolt-on to an RNN encoder-decoder, fixed the fixed-vector bottleneck on long sentences. Not yet the parallelization win. |
| <a id="vaswani-transformer"></a>Vaswani et al. — Attention Is All You Need (2017) | primary | transformers, attention | [arXiv:1706.03762](https://arxiv.org/abs/1706.03762) | high | Removed recurrence → parallelism → scaling → the LLM era. The architecture the frontier still runs on. |
| <a id="chen-stratton-bottlenecks"></a>Chen & Stratton — Artificial Intelligence in the Firm: Bottlenecks in Software Production (Harvard, Aug 2026) | primary | ai-in-sdlc, delivery, code-review | [fion.ac/jellyfish.pdf](https://fion.ac/jellyfish.pdf) | high | Staggered DiD on telemetry: 718 firms, 725,938 workers, 300M events, 2021–2026. Agents → +30% LoC / +20% commits / +23% PRs; shipped output insignificant (rules out >12%); review time +49%, bottleneck persists after AI review tools. Three separate coefficients, not a mediation. |
| <a id="nber-writing-vs-shipping"></a>Demirer, Musolff, Yang — Writing Code vs. Shipping Code (NBER WP 35275, 2026) | primary | ai-in-sdlc, delivery | [nber.org/papers/w35275](https://www.nber.org/papers/w35275) | high | 500k+ GitHub devs, matched event study: +240% commits / +80% projects / +30% releases, **cumulative over three tool generations**; gains "translated only partially into shipped and used software". |
| <a id="dora-2024"></a>DORA — Accelerate State of DevOps 2024 | primary | ai-in-sdlc, delivery, measurement | [2024_final_dora_report.pdf](https://services.google.com/fh/files/misc/2024_final_dora_report.pdf) | high | pp. 37, 39–40: per +25% AI adoption +7.5% docs / +3.4% code quality / +3.1% review speed, but −1.5% throughput and −7.2% stability. "AI adoption" = latent self-report scale of seven items (p. 30) — not a measured input. Never quote the DORA calculator's demo inputs as an effect. |
| <a id="dora-2025"></a>DORA — State of AI-assisted Software Development 2025 | primary | ai-in-sdlc, delivery, measurement | [dora.dev/dora-report-2025](https://dora.dev/dora-report-2025/) | high | Throughput sign reverses ("from negative to positive", p. 42); instrument changed to three items incl. *trust*, so 2024's −7.2% stability is neither confirmed nor refuted. |
| <a id="dora-2019"></a>DORA — Accelerate State of DevOps 2019 | primary | delivery, quality-gates, governance | [2019-dora-report.pdf](https://dora.dev/research/2019/dora-report/2019-dora-accelerate-state-of-devops-report.pdf) | high | p. 50: external change approval → 2.6× more likely low performer; "no evidence to support" it. ~1000 respondents, 3% margin of error. |
| <a id="meta-radar"></a>Automating Low-Risk Code Review at Meta — RADAR (2026) | primary | code-review, quality-gates, automation | [arXiv:2605.30208](https://arxiv.org/abs/2605.30208) | high | 535k+ diffs reviewed, 331k+ landed; p25→p50 risk threshold → 60.31% auto-approve; revert rate 1/3 and incident rate 1/50 of non-RADAR. Risk-selected funnel + observational before/after, not randomisation. |
| <a id="anthropic-auto-mode"></a>Anthropic — Claude Code auto mode (safety classifier), Mar 2026 | primary | quality-gates, agent-safety | [anthropic.com/engineering/claude-code-auto-mode](https://www.anthropic.com/engineering/claude-code-auto-mode) | high | 93% of permission prompts approved → approval fatigue; classifier 0.4% FPR (n=10,000 real traffic) and **17% FNR** (n=52 real overeager actions) — miss rate published by the system's own authors. |
| <a id="google-mutation-icse2021"></a>Google — mutants vs real bugs, coupling at scale (ICSE 2021) | primary | testing, mutation-testing, coverage | [arXiv:2103.07189](https://arxiv.org/abs/2103.07189) | high | ~400k mutants, >33M test-target runs, 1502 bugs; a mutant would have flagged 1043 (70%) at the introducing change — while **every** such change was already covered by tests: "coverage exhausted its usefulness". Retrospective on known bugs. |
| <a id="google-mutation-tse2021"></a>Google — mutation testing in industrial practice (TSE 2021) | primary | testing, mutation-testing | [arXiv:2102.11378](https://arxiv.org/abs/2102.11378) | high | 16,935,148 mutants, 10 languages, >24,000 developers. 85% initially judged unproductive → 82% productive after six years of hand-written per-language suppression rules. Google **rejected** the mutation score itself: "neither concrete nor actionable". |
| <a id="tricorder"></a>Tricorder: Building a Program Analysis Ecosystem (Google, ICSE 2015) | primary | static-analysis, quality-gates | [research.google pubs/43322](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/43322.pdf) | high | "Not useful" click rate with thresholds fixed in advance: ≥10% probation, >25% may be switched off. Caught a nine-week analyzer breakage (weeks 24→33 of 2014). Note: the paper says they *typically work with the analyzer author* — no unilateral veto claim. |
| <a id="mills-bebugging"></a>Mills — On the Statistical Validation of Computer Programs (IBM FSD, 1972) | primary | testing, defect-seeding | IBM FSD report (no stable public link; cited via secondary literature) | medium | Origin of bebugging / error seeding: plant known defects, estimate the *remaining* defects in the artefact. Our reading — using the same ratio to measure the **detector's sensitivity** — is ours, not Mills'. Say so when citing. |
| <a id="martin-xie-coverage"></a>Martin & Xie — A Fault Model and Mutation Testing of Access Control Policies (WWW 2007) | primary | testing, mutation-testing, coverage | [paper447.pdf](https://archives.iw3c2.org/www2007/papers/paper447.pdf) | high | 11 XACML policies, 906 mutants: **98.6% structural coverage at 47% mutants killed** — structural coverage is correlated with, but not strong enough for, fault-detection capability. |
| <a id="just-mutants-faults"></a>Just et al. — Are Mutants a Valid Substitute for Real Faults? (FSE 2014) | primary | testing, mutation-testing | [mutants_real_faults_fse_2014.pdf](https://homes.cs.washington.edu/~rjust/publ/mutants_real_faults_fse_2014.pdf) | high | 357 real faults, 321k lines: 17% not coupled to any mutant — "mostly involving algorithmic changes or code deletion". The honest limit of mutation testing. |
| <a id="meta-ach"></a>Meta — Assured LLM-based hardening / ACH (2025) | primary | mutation-testing, llm-testing | [arXiv:2501.12862](https://arxiv.org/abs/2501.12862) | high | 10,795 classes, 31,677 generated faults, 9,095 (29%) compile; 571 unit tests generated, 73% of 191 reviewed accepted. Table 8: **277 of 571 (49%)** mutant-killing tests add no line coverage at all. Authors: "no way to consistently and reliably measure problem similarity or relevance". |
| <a id="porter-votta-basili"></a>Porter, Votta & Basili — Comparing Detection Methods for Software Requirements Inspections: A Replicated Experiment (UMD tech report / TSE 1995) | primary | inspections, requirements, defect-seeding | [drum.lib.umd.edu](https://drum.lib.umd.edu/bitstreams/332d6328-bdce-4726-9102-e00bac748f9a/download) | high | 48 participants, 16 three-person teams; teams find 24–57% of faults; collection meetings gave **no net improvement**. Deliberately refused to seed: "No faults were intentionally seeded … All faults are naturally occurring." Note the link resolves to the UMD report, not the TSE paper. |
| <a id="eicar-testfile"></a>EICAR anti-malware test file | secondary | defect-seeding, testing | [eicar.org](https://www.eicar.org/download-anti-malware-testfile/) | high | The canonical known-bad artefact for testing a detector: "Using real viruses for testing … is rather like setting fire to the dustbin in your office to see whether the smoke detector is working." |
| <a id="sre-workbook-alerting"></a>Google SRE Workbook — Alerting on SLOs | secondary | monitoring, quality-gates | [sre.google/workbook/alerting-on-slos](https://sre.google/workbook/alerting-on-slos/) | high | Worked example where an alert can never fire: 90% target + "2% of budget in an hour" threshold, a 100% outage burns 1.4%. The arithmetic of a dead detector, written by its own authors. |
| <a id="architecture-conformance"></a>Architecture conformance checking — Knodel, Muthig & Rost (ICSM 2008) + Olsson et al. (ECSA-W 2016) | primary | architecture, fitness-functions | [DOI 10.1109/ICSM.2008.4658077](https://doi.org/10.1109/ICSM.2008.4658077) · [Olsson 2016](https://urn.kb.se/resolve?urn=urn:nbn:se:lnu:diva-60472) | medium | Comparative measurements of automated architecture checks (six teams, 2008; eight student projects, 2016).
